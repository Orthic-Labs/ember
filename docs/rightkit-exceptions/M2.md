# RightKit M2 (app frame): Ember's exceptions

> **Last updated:** 2026-10-19

Ember's desktop web UI (`apps/lightcraft-desktop/web/src`) builds its frame from the published M2 packages:

- @rightkit/react-shell 0.7.1
- @rightkit/platform-ui 0.4.0
- @rightkit/theme 0.3.1

The frame code those packages cover has been deleted: dialogs, form controls, menus, popovers, the nav list, toasts and theme application. The behaviours below stay in the app because the published API has no equivalent.

Each one is recorded in [`.rightkit/ownership-exceptions.json`](../../.rightkit/ownership-exceptions.json) (capability `app-shell-ui`, package `@rightkit/react-shell`). For each, this page gives four things:

1. what the user loses if it is removed;
2. why the published API can't do it;
3. how other apps handle it;
4. proof.

Citations are to `@rightkit/react-shell` 0.7.1, `dist/react/*.d.ts`.

## 1. Inspector resizer

**Code:** `App.tsx` (`resizeInspectorByKey`, the inspector drag handle) and the `--lc-inspector` width rules in `app.css`.

**What the user loses:** the right-hand develop inspector can no longer be resized (260–520 px) with the pointer or the keyboard (Left and Right arrows, Shift for larger steps, Home and End). Users who need wide panels for the curve and colour tools would be stuck at one width.

**Why the published API can't do it:** `sidebarResizable` and `onSidebarWidthChange` resize only the left sidebar (`layout.d.ts:278-287`). There is no right-hand panel, splitter or resize primitive in `dist/react/*.d.ts` or the README.

**How other apps handle it:** they keep their own right-panel sizing too:
- CodeRight sizes its right dock itself (`coderight/apps/coderight-tauri/src/components/app/AppBody.tsx:177`).
- CutRight has its own resize separator (`cutright/apps/cutright/src/editor/TimelineEditorView.tsx:367-368`).

**Proof:**
- `inspectorWidth` is persisted in the UI state.
- The native journey asserts the collapsed layout through `.lc-stage-layout.is-inspector-collapsed` (`apps/lightcraft-desktop/tests/native_qualification.rs`).
- To reproduce, drag the inspector's left edge or focus it and press Home or End.

## 2. Collapsed sidebar as an icon rail

**Code:**
- `App.tsx`: `sidebarWidth={ui.sidebarCollapsed ? 48 : ui.sidebarWidth}`.
- `app.css`: the collapsed `.rk-side` rules that keep the sidebar visible with labels hidden.

**What the user loses:** collapsing the library sidebar would hide it entirely. Today it shrinks to a 48 px rail of source icons (All Photos, albums, folders), so the user can still switch source without reopening the sidebar.

**Why the published API can't do it:** `sidebarCollapsed` and `onSidebarCollapsedChange` (`layout.d.ts:265-266`) hide the sidebar. The shell CSS has only `.rk-shell.is-collapsed .rk-top__side` rules and no rail mode.

**How other apps handle it:** suite apps with a collapsible sidebar either let it hide completely (the published behaviour), or keep their own expanded or collapsed panel, as ViewRight does (`viewright/src/app/sidebar/SidebarExpandedPanel.tsx`). Ember follows the photo-library convention of a persistent source rail.

**Proof:** collapse the sidebar (titlebar toggle or the sidebar chord). The 48 px icon rail stays, and clicking an icon switches the source.

## 3. RetainedLayout

**Code:** `layout/RetainedLayout.tsx`, used by `App.tsx` around the stage and inspector.

**What the user loses:** switching between grid, loupe, compare and survey, or collapsing the inspector, changes the layout geometry. Without RetainedLayout, React remounts the stage and inspector subtrees, which loses:
- the scroll position in the photo grid;
- in-flight preview state and the decoded images held by the stage;
- the inspector's open sections and focus.

Each view switch would reload previews and jump the grid to the top. RetainedLayout keeps the stateful children in one portal host and moves that host between geometry shells (`moveBefore` where WebKit supports it).

**Why the published API can't do it:** none of the three M2 packages offers a retained portal host or any layout-change primitive that preserves child state. `@rightkit/react-shell` provides only `AppShell` slots (`layout.d.ts`).

**How other apps handle it:** no other suite app swaps whole layout geometries around a heavy stateful image surface. Their workspaces keep one geometry.

**Proof:** switch from Grid (G) to Detail (D) and back. The grid keeps its scroll position and the active photo's preview does not reload. The native journeys that move between grid and detail (`.lc-grid-window`, `.lc-filmstrip`) depend on this.

## 4. Inert background while a dialog is open

**Code:** `dialogs/inertSiblings.ts`, used by the dialog `Frame` in `dialogs/DialogHost.tsx` and by `dialogs/CullReviewDialog.tsx`.

**What the user loses:** while a dialog is open, the page behind it would stay focusable and visible to assistive technology. Screen-reader and keyboard users could reach controls behind the modal, for example starting a second import while the Import dialog is open.

**Why the published API can't do it:** `ModalShell` and `Dialog` trap focus and close on Escape (`overlays.d.ts:48-51` lists the behaviours), but they set neither `inert` nor `aria-hidden` on siblings. There is no match for either in `overlays.js`, `focus.js`, `hooks.js` or the README.

**How other apps handle it:** suite apps whose dialogs are short confirmations rely on the focus trap alone. Ember's dialogs are long-running and editable (import, export, merge, cull review) and sit over a live library that keeps updating, so it also blocks the background.

**Proof:** the native journey asserts that the root is inert and that the dialog and backdrop are not (`rootInert` / `dialogInert` in `apps/lightcraft-desktop/tests/native_qualification.rs`).

## 5. TextArea

**Code:** `TextArea` in `dialogs/DialogHost.tsx`, and the multi-line textarea in `inspector/Inspector.tsx`.

**What the user loses:** multi-line input. The export watermark text spans lines, and the same applies to captions and keyword lists.

**Why the published API can't do it:** `ui.d.ts:16` exports `Input` only. Neither react-shell nor platform-ui ships a textarea component.

**How other apps handle it:** apps that need a multi-line field use a plain `<textarea>` inside the published `Field`. Ember's `TextArea` is the same thing, kept as one component so every multi-line field is labelled the same way.

**Proof:** the export journey types `"MMMM\nMMMM"` into "Watermark text" and asserts that the newline survives (`native_qualification.rs`, "multiline watermark must survive React input").

## 6. Develop-slider gestures

**Code:** `ControlRow` in `inspector/Inspector.tsx`.

**What the user loses:** a develop-slider drag that settles as one undo step. Escape cancels the gesture, arrow keys settle after 400 ms, and the input keeps its stable `id="ctl-<control>"` for automation.

**Why the published API can't do it:** `Slider` (`ui.d.ts:94-105`, `ui.js:53-54`) renders a range input with only `onChange`. It has no pointer-down, pointer-up or cancel hooks, no key hooks, and no `id` prop.

**How other apps handle it:** no other suite app has a slider whose gesture is an undoable unit. Their sliders apply on change.

**Proof:** the develop journey asserts that "sustained pointer drag must settle as one undo step" (`apps/lightcraft-desktop/tests/native_qualification.rs`).

The grid photo menu's rating and label choices are no longer an exception. They are published checkable `ContextMenu` rows (rightkit M2 validation of f0048306).

## 7. Focus return when the opener is gone

**Code:**
- `dialogs/focusReturn.ts` (`useFocusHistory`, `useReturnFocus`), used by the dialog `Frame` in `dialogs/DialogHost.tsx`.
- `closePanel` in `BackgroundActivity.tsx`.

**What the user loses:** when a dialog opens from the command palette (for example Settings), or the Background activity panel opens from a click, closing it leaves keyboard focus on `<body>`. Keyboard and screen-reader users then lose their place and must Tab from the top of the window. That is an accessibility regression, which lead rule 7 forbids.

**Why the published API can't do it:** `ModalShell`, `useFocusTrap` and `Popover` record the opener once, when they first render (`popover.js:19`, `opener = useRef(document.activeElement)`). In WebKit a click doesn't focus a button, so the recorded element is `<body>`. When a dialog opens from the palette, the palette input unmounts as the dialog renders. Either way the published restore has nothing valid to return to, and none of the three takes a `returnFocus` target or fallback.

**How other apps handle it:** no other app lists this exact need in its M2 order. The closest is S12 in the cross-app summary (`CROSS-APP-M2.md`): ViewRight keeps its own dropdown because `Popover` takes focus. Ember differs because its dialogs open from a palette that unmounts, and its panel trigger is clicked in WebKit.

**Proof:** the native journeys assert the return target:
- after Escape closes the settings modal, `focus must return to actual pre-modal target`;
- after the Background activity panel closes, `document.activeElement === .lc-background-activity > button`.

Both are in `apps/lightcraft-desktop/tests/native_qualification.rs`. Ember's code acts only when focus has fallen to `<body>`, so it never overrides the published restore.
