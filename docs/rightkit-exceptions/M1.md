# RightKit M1 (window host): Ember's exceptions

> **Last updated:** 2026-10-19

Ember's desktop app (`apps/lightcraft-desktop`) is on the M1 owners:

- rightkit-tauri-shell `=0.4.0`
- rightkit-device `=0.3.1`
- @rightkit/tauri `0.2.3`

The code the published API covers is deleted:

- **Second window:** created by `rightkit_tauri_shell::windows::open`.
- **Fullscreen without an explicit state:** goes through `rk_shell_window("fullscreen")`.
- **Ordinary close:** goes through `rk_shell_window("close")`.

Four window behaviours stay in the app because the published API (shell 0.4.0) has no equivalent. Each is recorded in [`.rightkit/ownership-exceptions.json`](../../.rightkit/ownership-exceptions.json) (capability `desktop-shell`, package `rightkit-tauri-shell`) and explained below:

1. what the user loses if it is removed;
2. why the published API can't do it;
3. how other apps handle it;
4. proof.

## 1. Fullscreen to an explicit state

- **Code:** `apps/lightcraft-desktop/src/native.rs`, `toggleFullscreen` with `enabled`.
- **What the user loses:** Full Screen Preview (`F`) and the stage's Fullscreen button set fullscreen *on* (or *off*), not "the opposite of now". With a toggle only:
  - pressing Full Screen Preview while already fullscreen would leave fullscreen;
  - a QA journey that asks for fullscreen could not establish the state it needs.
- **Why the published API can't do it:** the shell's `"fullscreen"` action only toggles: `window.set_fullscreen(!window.is_fullscreen())` (rightkit-tauri-shell 0.4.0 `src/commands.rs:118-120`). `WindowSpec.fullscreen` applies only when a window is created (`src/windows.rs:71-72`, `256-257`).
- **Other apps:** cutright sets fullscreen explicitly in its media adapter (`mediaAdapters.ts:18`). Ember differs because it routes the explicit form through its command system (`view.fullScreenPreview`, `view.enterFullScreen`), which takes an `enabled` parameter.
- **Proof:** `desktop.tsx:439` passes `enabled`, and `StageWorkspace.tsx` calls `onNative("fullscreen", { enabled: true })`. To reproduce, enter fullscreen and press F. It must stay fullscreen.

## 2. Close guard for the main window

- **Code:** `native.rs` `.on_window_event` `CloseRequested` for `main`, plus the `closing` / `shutdown_complete` state.
- **What the user loses:** closing the main window while an import, export or preview build is running, or while the catalog has unsaved changes, would quit without the guard:
  - running work would be lost;
  - the "save before closing?" prompt (`lc://close-requested`) would never appear;
  - the session owner would not be shut down in order (`host.shutdown_process`), so the catalog journal would not be flushed.
- **Why the published API can't do it:** the shell's `CloseRequested` handler only saves window state and implements close-to-tray (rightkit-tauri-shell 0.4.0 `src/lifecycle.rs:533-545`). There is no hook through which the app can veto or defer a close. The quit drain in `quit.rs` covers `ExitRequested`, not a window close.
- **Other apps:**
  - pulse destroys the window on close (`lib.rs:660-669`);
  - heardright runs a close animation (`app_run.rs:546-574`).

  Neither has to protect unsaved document state.
- **Proof:** `active_close_reason` (`native.rs`), the unsaved-close path that emits `lc://close-requested`, the handler at `desktop.tsx:698`, and the forced close from `DialogHost.tsx:219` after the user confirms.

## 3. Focus and drop events to the renderer

- **Code:** `native.rs` `.on_window_event` emits `lc://window-focus` (Focused) and `lc://native-drop` (DragDrop).
- **What the user loses:** dropping photos or folders on the window would no longer import them, and the renderer would not know when the window regains focus (a refresh of library state).
- **Why the published API can't do it:** the shell consumes `Focused` internally for idle tracking and lifecycle (`src/lifecycle.rs:522-523`) and does not emit it to the app. It has no drag-drop forwarding.
- **Other apps:**
  - viewright forwards focus itself (`lib.rs:661-668`);
  - genright uses `onDragDropEvent` in the webview.

  Ember keeps the native forwarding so dropped paths reach the Rust import path as filesystem paths.
- **Proof:** the listeners at `desktop.tsx:678` (`lc://native-drop`) and `desktop.tsx:694` (`lc://window-focus`).

## 4. QA viewport geometry

- **Code:** `native.rs` `qa_viewport` (window `set_size` and `outer_position`), used only with the `qa-native` feature.
- **What the user loses:** nothing in a release build. Without it, native QA can't set and verify window geometry. The readback half already uses the shell's `windows::readback`.
- **Why the published API can't do it:** the shell exposes `windows::readback` (`src/windows.rs:481`) but no API to set the size or read the outer position of an existing window.
- **Other apps:** none.
- **Proof:** `set_native_viewport` and `diagnose_native_viewport_bounce` in `apps/lightcraft-desktop/tests/native_qualification.rs` (lines 613, 644).
